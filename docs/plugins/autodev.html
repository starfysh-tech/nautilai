autodev

Test-driven development loop: work a plan or ticket to done, blocked, or needs-guidance, red test first, one slice at a time.

Install

/plugin install autodev@nautilai

What it does

AutoDev takes a plan or ticket(s), plans each lane with the complexity quadrant and Given/When/Then scenarios, and stops once at a launch checkpoint to confirm seams, scenarios, and the first red test's real failure output. Then each slice runs red, then green: the orchestrator writes and commits a red test, a disposable haiku worker makes it pass, scripts verify, an independent review-gate agent reviews, and the change is committed on the lane branch. Guards the spec demands are proven by removing each one and requiring its test to fail.

The scripts are covered by offline suites; the end-to-end TDD flow has not run live yet. Earlier live runs covered one macOS machine over npm and pytest suites — see the README's "Validated scope".

Commands / skills

  • /autodev <plan or ticket(s) | path or URL>

    Runs the full flow: TDD profile, lane planning, existing-test review, baseline, first red test, launch checkpoint, then red/green slices, guard checks, one refactor attempt, and either DONE.md or an escalation summary.

    "run this ticket to completion", "work this plan test-first", "keep trying until it's done or blocked"
  • /autodev --setup

    Detects the repo's test, lint, format, coverage, and DB-isolation commands, shows each with its source file, and writes the confirmed TDD profile to .claude/autodev.md.

    explicit slash form only
  • /autodev --plan-only <plan or ticket(s)>

    Runs to the launch checkpoint and stops; a later run on the same input starts at the slices.

    explicit slash form only
  • /autodev --review-tests <path>

    Read-only review of existing tests: FIRST-U scores, anti-patterns, missing scenarios, proposed fixes, and coverage gaps.

    explicit slash form only
  • /autodev --unattended <plan or ticket(s)>

    An advisor agent answers the stops; every decision is logged for you to validate at the end.

    explicit slash form only

How it works

  • TDD rules ship in references/tdd.md; each lane gets a frozen cut per role — TDD-worker.md and TDD-review.md — with only the stacks the repo's TDD profile lists.
  • One task lane per independent task, with state in .autodev/<slug>/ and a scripted worktree on an autodev/<slug> branch. Baseline verification must pass before any red test is written.
  • Red tests are written by the orchestrator one slice at a time; expect_run.sh red rejects a timeout, a missing command, or an empty collection as a red, and the test is committed before the worker starts.
  • verify.sh runs a pipeline: red tests and test config unchanged since the red commit, red tests, lint and format check on changed files, lane VERIFY.sh, full suite. Coverage is reported, never gated.
  • An independent review-gate agent checks the diff against TASK.md and the lane's test anti-pattern list; expect_run.sh guard removes each guard in a throwaway worktree and requires its test to fail.
  • Failures are classified and fingerprinted; 3 counted failures per slice, or a repeated identical fingerprint, stop the lane with a guidance handoff. Up to 5 parallel_safe lanes run at once.

Under the hood
  • State lives in .autodev/<slug>/ — TASK.md, RUNSTATE.md, DONE.md, TDD-worker.md, TDD-review.md, a frozen profile.md, optional lane VERIFY.sh, all self-gitignored.
  • The TDD profile .claude/autodev.md holds YAML frontmatter (test_file, full_suite, lint, format, format_check, coverage, db_isolation, test_config, stack) read by profile.py; an empty value is an error, unknown is a logged skip.
  • init_task_lane.sh / create_worktree.sh — lane files + controller state, then a worktree at .autodev-worktrees/<slug> on an autodev/<slug> branch.
  • baseline_verify.sh — must pass before autonomous work starts.
  • verify.sh — the TDD pipeline for lanes with a profile; otherwise lane VERIFY.sh, else auto-detected npm/pytest/go/cargo. Receives AUTODEV_PHASE (baseline skips the red and lint stages). Times out after AUTODEV_VERIFY_TIMEOUT seconds (default 1200), killing the process group.
  • commit_lane.sh / commit_path.sh — red, green, and refactor commits stage only named files and always run hooks; /commitcraft commit --files is used when CommitCraft is installed for the repo.
  • classify_failure.sh / fingerprint_failure.sh — bucket a failure log (implementation / environment / specification / transient) and hash it; only implementation failures count toward the 3-cap. Ambiguous logs default to implementation, since a misclassified failure would be an uncounted retry.
  • The review-gate agent runs on sonnet and the advisor on opus, distinct from the haiku worker attempts. The advisor never decides changes outside the lane branch, secret-scanner hits, or anything irreversible.
  • controller.sh — the state machine over .autodev/state.json; escalate_summary.sh writes the guidance handoff after a hard stop.
  • No hooks are installed — verification runs only inside the /autodev loop.
  • The worker never creates DONE.md — only the orchestrator, after verify.sh passes.

Requirements

Claude Code with plugin support, python3, and a test runner that can run a single test file (recorded in the TDD profile by /autodev --setup). Tasks with no testable behavior use a lane VERIFY.sh. No hooks are installed; verification runs only inside the /autodev loop.
