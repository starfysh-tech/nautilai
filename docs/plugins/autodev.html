autodev

Bounded autonomous development loop: work a ticket to done, blocked, or needs-guidance — without grinding indefinitely or grading its own homework.

Install

/plugin install autodev@nautilai

What it does

AutoDev takes a ticket or plan and runs it through a bounded autonomous loop: an isolated worktree per lane, disposable haiku worker subagents that make the smallest useful change, and objective script-based verification instead of model self-judgment. A hard stop after 3 counted implementation failures produces a guidance handoff instead of grinding on.

Validated across five live runs on one macOS machine, over npm and pytest suites — see the README's "Validated scope" for what hasn't been exercised yet (Linux/CI, the native installed-plugin path, and a live pass through the review gate).

Commands / skills

  • /autodev <ticket text | plan text | path or URL>

    Runs the given task through the full lane lifecycle: init, worktree, baseline verify, bounded worker attempts, verification, review gate, and either DONE.md or an escalation summary.

    explicit slash form only

How it works

  • One task lane per independent task, with state in .autodev/<slug>/ and a scripted worktree on an autodev/<slug> branch — the model never manages worktree mechanics by hand.
  • Baseline verification must pass before autonomous work starts, so pre-existing breakage is never billed to the worker.
  • Each attempt is one bounded haiku-worker run; verify.sh (a lane VERIFY.sh, or an auto-detected npm/pytest/go/cargo suite) decides completion, not model self-judgment.
  • Tests-green is necessary but not sufficient: an independent review-gate agent checks the lane diff against TASK.md for what tests can't see — resource lifecycle, scope creep, weak new tests, security patterns. A blocking verdict counts as an implementation failure toward the same cap; only a pass yields DONE.md.
  • Failures are classified (implementation / environment / specification / transient) and fingerprinted; only implementation failures count toward the cap. After 3 counted failures, or a repeated identical fingerprint, the lane stops and produces a concise guidance handoff.
  • Up to 5 lanes can run in parallel, gated by a conservative parallel_safe heuristic.

Under the hood
  • State lives in .autodev/<slug>/ — TASK.md, RUNSTATE.md, DONE.md, optional lane VERIFY.sh, all self-gitignored.
  • init_task_lane.sh / create_worktree.sh — lane files + controller state, then a worktree at .autodev-worktrees/<slug> on an autodev/<slug> branch.
  • baseline_verify.sh — must pass before autonomous work starts.
  • verify.sh — lane VERIFY.sh wins, else auto-detected npm/pytest/go/cargo; receives AUTODEV_PHASE (baseline | attempt). Times out after AUTODEV_VERIFY_TIMEOUT seconds (default 1200), killing the process group.
  • classify_failure.sh / fingerprint_failure.sh — bucket a failure log (implementation / environment / specification / transient) and hash it; only implementation failures count toward the 3-cap. Ambiguous logs default to implementation, since a misclassified failure would be an uncounted retry.
  • The review-gate agent runs on the sonnet model, distinct from the haiku worker attempts.
  • controller.sh — the state machine over .autodev/state.json; escalate_summary.sh writes the guidance handoff after a hard stop.
  • No hooks are installed — verification runs only inside the /autodev loop.
  • The worker never creates DONE.md — only the orchestrator, after verify.sh passes.

Requirements

Claude Code with plugin support, and an existing test suite the auto-detector can run (npm/node --test, pytest, or a lane-supplied VERIFY.sh for anything else — go/cargo detection exists but is unexercised). No hooks are installed; verification runs only inside the /autodev loop.
