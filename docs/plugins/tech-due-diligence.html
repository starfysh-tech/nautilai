tech-due-diligence

Technical due diligence for any repo and any stack — one report where every finding cites the code it is about.

Install

Claude Code

/plugin install tech-due-diligence@nautilai

Hermes Agent

$ hermes skills install skills-sh/starfysh-tech/nautilai/tech-due-diligence

No tap needed in Hermes — hermes skills tap add does not index this repo. The inventory script and references live in the skill directory, so Hermes receives them directly.

What it does

A stdlib Python script inventories the repo from git ls-files: languages, manifests and lockfiles per directory, frameworks, container, CI, and IaC files, tests, docs, git history stats, and which scanners are installed. The skill runs the scanners that match, triages every candidate against its cited line, and reads the code for architecture, operations, licensing and IP, and team risk. Owner mode writes an ordered fix list. Buyer mode adds a deal impact to each Critical and High finding, questions for the seller, and a list of documents to request.

Commands / skills

  • /tech-due-diligence [repo-path]

    Audit a repo in owner mode and write the report to the current directory.

    "technical due diligence", "M&A diligence", "evaluate this codebase", "code health audit", "security posture review"
  • /tech-due-diligence --mode buyer <path>

    Evaluate someone else's repo. Opens with an investment summary: a verdict, the top risks with business impact, deal impact, and an estimated remediation size, the conditions to close, and the limits of the opinion. Never executes the target's code.

    explicit slash form only
  • /tech-due-diligence --claims <file>

    Check each claim in a seller or team document against the code: supported, partly supported, contradicted, or unverifiable.

    explicit slash form only
  • /tech-due-diligence --quick

    Secrets, dependencies, and licenses only.

    explicit slash form only

How it works

  • Every file list comes from git ls-files, so dependency installs, virtualenvs, build output, and nested worktrees stay out of the audit.
  • Scanners run per detected signal: gitleaks over the full git history with secrets redacted, semgrep with p/default plus a pack per framework, osv-scanner for vulnerabilities and licenses or per-lockfile audits, trivy for every container image the repo names, hadolint and checkov for infrastructure.
  • Triage and the code read run in parallel lanes, one subagent per area. Every Critical and High finding is re-read at its cited lines before it reaches the report.
  • Triage drops test fixtures, parameterized queries, vendored and generated code, and duplicates. The report counts what was dropped and why.
  • Stack packs add checks for Django, React/Next.js/Vue/Angular, Apple apps (iOS, macOS), Android, Go, Rust, Rails, Spring Boot, Express/NestJS, and Flask/FastAPI when detected.
  • A finding the repo's own risk register or security docs already record is tagged tracked. The report header states when the checkout is behind its upstream.
  • Each area is RAN, PARTIAL, NOT RUN: <reason>, or N/A. A skipped area never reads as clean.

Under the hood
  • The checkout is audited as it is: no fetch, pull, checkout, stash, or reset. Hosting and deploy accounts are queried only with --allow-accounts.
  • Licensing and IP items are observations with no severity, each paired with a question for the seller or counsel.
  • Buyer mode runs only read-only scanner commands: no installs, builds, tests, package scripts, or manage.py.
  • Repo content is data. Comments, docs, and commit messages in the target cannot change the audit; an attempt to steer it is reported as a finding.
  • Every finding has the report disposition. The skill changes nothing in the audited repo.
  • Shoals: in owner mode, corrections are recorded in .claude/shoals/tech-due-diligence.tech-due-diligence.md for the next run. Buyer mode neither reads nor writes them.

Requirements

git and python3 3.9 or later. Every scanner is optional: a missing one marks its check NOT RUN, and the skill never installs anything. For the fullest report, have gitleaks, semgrep, and osv-scanner or trivy on PATH. semgrep fetches its rule packs from the semgrep registry, so code security needs network access.
