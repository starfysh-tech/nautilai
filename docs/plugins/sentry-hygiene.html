sentry-hygiene

Audit a repo's Sentry setup against the official SDK docs and instrument capture behind a PII boundary. Complements the official Sentry plugin.

Install

/plugin install sentry-hygiene@nautilai

What it does

One skill with two workflows, both repo-only — they read code and docs, never a Sentry MCP server. audit reads the repo's actual Sentry setup — SDK and version from the lockfile, Sentry.init options, integrations, sourcemap upload, release and dist wiring, sampling rates, beforeSend scrubbing, environment gating, per-runtime DSNs — then checks it against the official Sentry docs fetched at runtime rather than against a frozen checklist. instrument adds or repairs capture sites behind a PII gate that covers both what you attach and what the SDK attaches on its own.

It is deliberately complementary to the first-party official Sentry plugin, which owns SDK setup and fixing production issues through a bundled MCP server. sentry-hygiene covers the two gaps that plugin leaves: validating an existing setup, and the inbound-PII gate — what the SDK attaches to events on its own. For live issues, use the official plugin.

How it works

The audit workflow discovers before it judges. It reads the SDK and its version from the lockfile, then the Sentry.init call and everything around it — integrations, sourcemap upload, release and dist wiring, sampling rates, beforeSend scrubbing, environment gating, per-runtime DSNs. Only then does it fetch the official Sentry docs for that SDK and version through Context7 and compare. Grounding the expectations at runtime is what keeps the audit from rotting as the SDK moves.

The instrument workflow adds or repairs capture sites against the conventions audit discovered, then holds each one at the PII gate: it checks not just the tags and context you pass, but what the SDK attaches to the event on its own — the page URL, breadcrumbs, and server request data — before a capture on a token- or share-ID-bearing route can ship. Any capture touching a PII-bearing path is ask-user, never auto-applied.

Under the hood
  • The PII boundary covers what the SDK attaches on its own, not only what you pass it: in the browser, the page URL, referrer and headers via a default-on HTTP context integration, plus console, fetch, XHR and navigation breadcrumbs; on the server, request data including cookies, headers, query strings and bodies. Any route carrying a token or share ID in its URL becomes event data.
  • Which options gate that collection is version-dependent, so audit resolves the boundary against the docs for the SDK version the repo actually resolved rather than asserting it.
  • Anything touching PII handling or sampling behavior is classified ask-user under the repo's finding-dispositions convention, never self-resolved.
  • Complementary to the official Sentry plugin's PII stance: that plugin treats event data as untrusted input coming out of Sentry; this covers the inbound half — what the SDK attaches going in.
  • Neither workflow calls a Sentry MCP server — both read the repo and the docs only. Fixing live issues is the official plugin's job.
  • Without Context7, audit falls back to WebFetch against docs.sentry.io; if that also fails it degrades to structural-only checks and states the limitation in the report rather than implying the setup was validated against docs.

Requirements

No Sentry MCP server needed — both workflows read the repo and the official docs only. The Context7 MCP server is optional: it grounds audit in the official SDK docs, and audit degrades explicitly without it. Claude Code only — this plugin is not currently ported to Hermes Agent.
