ontology

A local-first, technology-agnostic map of how an application works, queried by coding agents before they read code.

Install

/plugin install ontology@nautilai

What it does

It keeps a typed graph of how the repo’s application works, in the domain’s own words: areas of responsibility, actors, capabilities, domain concepts, processes, events, rules, and decisions. It records behavior, never the stack, so the map stays true through a rewrite. An onboarding wizard seeds the graph from the repo, and agents orient with it before opening files. Every write is checked against a schema. Nothing in the graph points at code, not even a file path.

Commands / skills

  • /ontology setup

    Onboarding wizard: choose local or shared storage and a vocabulary, survey the repo, approve the seed, and optionally add a pointer to CLAUDE.local.md or CLAUDE.md.

    “set up the ontology”, “map this codebase”
  • /ontology refresh

    Review the map against the code: pick the areas whose behavior recent commits touched, compare, and fix the map behind an approval.

    explicit slash form only
  • /ontology <question>

    Answer from the map. The skill also loads on its own when a coding task starts in a repo with a .ontology/ directory.

    “what depends on X”, “where is X handled”, “how does X work”

How it works

The setup wizard builds the map in one guided pass. Nothing is written until you approve the seed.

1check for a storeontology.py status
2ask storage, vocabulary, depth
3create the storeontology.py init
4survey the repo
5dry-run the seedapply --dry-run
6you approve
7write the graphontology.py apply

The map has no links to code, so it cannot detect drift by itself. A refresh is a review the agent runs against recent changes.

1read recent commits/ontology refresh
2pick affected areas
3compare code with map
4you approve fixes
  • .ontology/schema.json defines the allowed types and relations; .ontology/graph.jsonl is an append-only log replayed on read.
  • By default .ontology/.gitignore ignores the whole directory, so the map stays local. The wizard's Shared option makes it committable.
  • The agent adds behavior it confirmed in code and corrects entities the code contradicts in the area it touched, then lists those writes. It asks before removing an entity, changing a Decision or Rule, or editing the schema.
  • The graph holds behavior only. Types accept only the properties they define and the engine refuses a sources field, so no file path, language, framework, vendor, table, or endpoint can be recorded.
Under the hood
  • scripts/ontology.py is the engine: Python standard library only.
  • Writes are rejected for an unknown type or relation, a missing required property, a value outside an enum, the wrong endpoint types, a cardinality breach, a cycle in an acyclic relation, a link to a missing entity, or a property named like a secret.
  • apply checks a JSONL batch line by line against the graph as it would be after each earlier line, and writes nothing if any line fails.
  • Removing an entity removes every relation touching it. A repeated link is a no-op.
  • Templates: application (Area, Actor, Capability, Concept, Process, Event, Rule, Decision) and empty.
  • ONTOLOGY_DIR overrides the store location. Exit codes: 0 success, 1 validation failure or not found, 2 bad usage or no store.

Requirements

Python 3.10 or later; the engine uses only the standard library. Git is optional: with git the map is stored at the repo root, and without it in the current directory.
