worktree-lanes

Run several branches of a repo at once, each in its own git worktree with its own env file, ports, linked deps, and route — driven by a per-repo recipe.

Install

/plugin install worktree-lanes@nautilai

What it does

A lane is a git worktree on its own branch that runs like the main checkout: its own env file, its own ports, dependencies linked or installed, an optional service route, and optionally its services started. The bundled engine, scripts/lane, does that work for any stack; everything stack-specific lives in a per-repo .lanerc recipe — a sourced shell file of hooks and variables. /worktree-lanes --setup discovers the stack, shows each detected piece with its source file, and drafts the recipe for you to confirm. After that, opening a lane is one command.

The engine is generic, but a stack's install and start hooks are only as good as the recipe written for it; setup smoke-tests a throwaway lane to prove the recipe before calling it done.

Commands / skills

  • /worktree-lanes --setup

    Discovers this repo's stack — dependency installs, services, and which values must differ per lane — and drafts a .lanerc at the repo root for you to confirm and commit.

    "set up worktree lanes"
  • /worktree-lanes <slug> [--proxy | --isolated]

    Opens a lane named <slug> on a new branch, in host mode by default, and reports the lane path, mode, and per-lane ports.

    "run parallel branches", "work on several features at once", "open a dev lane"

How it works

  • The engine owns the worktree, the env file, port allocation, dependency linking, routing, and the lane lifecycle. The recipe supplies optional hooks (lane_project, lane_env, lane_setup, lane_route, lane_start, lane_stop, lane_retire, lane_gc) and variables (LANE_LINK_DIRS, LANE_PORT_VARS, LANE_ENV_FILE, …). A hook the stack doesn't need is simply omitted.
  • Bootstrap from main, run from the lane: the recipe is always sourced from the main worktree, so the bootstrap never drifts with the branch under test, and its hooks run with CWD set to the lane.
  • Three modes. host (default) shares the database and uses no hostnames; proxy (--proxy) shares the database and gives the lane its own hostnames through a reverse proxy; isolated (--isolated) has the recipe provision the lane's own database and stack, and is available only when the recipe declares support for it.
  • Install or link, per dependency: lane_setup installs per lane by default; a directory in LANE_LINK_DIRS is symlinked from main only when it is identical on every branch, since installing through the link changes main's copy. The linker never replaces a real file with a symlink.
  • Ports: each KEY:base pair in LANE_PORT_VARS becomes base + stride × offset. Offsets start at 1 (main is 0), and allocation runs under a repo lock, skipping any offset whose ports clash with main, another lane's reservation, ports recorded by lanes made with other tooling, or a listening socket.
  • rm refuses any uncommitted change except the engine's own artifacts (the untracked env file and link symlinks), and a failing teardown hook, unless --force; then it retires the lane's route, stops its services, and removes the worktree, keeping the branch. gc runs the recipe's sweep first and only then releases the offsets of vanished lanes, so a stale route can't serve the next lane that inherits its port.

Under the hood
  • lane open <slug> [--proxy|--isolated] [--start] [--base <ref>] — cuts branch <slug> from origin/<base>, else local <base>; fails if neither resolves.
  • lane pr <number> [--proxy|--isolated] [--start] — a lane named pr-<number> on the PR's own branch, via gh pr checkout.
  • lane resume <slug> [--start] [--env] — finishes an interrupted open, re-running setup and route; --start (re)starts services; --env regenerates the env file after a recipe fix.
  • lane rm <slug> [--force], lane ls (branch, mode, offset, ports per lane), lane gc.
  • Services start only with --start; without it the lane is ready but idle.
  • Lanes live under LANE_ROOT (default .claude/worktrees); new branches cut from LANE_BASE_BRANCH (default main); ports are spaced by LANE_PORT_STRIDE (default 100).
  • The lane's env file starts as a copy of main's LANE_ENV_FILE (LANE_ENV_COPY=0 to start empty); every key the engine or lane_env sets then replaces all earlier definitions of it (export and CRLF forms included). lane_env may not set LANE_* or allocated port keys. Before every write the file must be untracked, not a symlink, and inside the lane.
  • Each hook runs in its own bash process with set -euo pipefail, so however the engine calls it, a hook that fails stops the verb and keeps the lane for lane resume (bash's usual errexit limits still apply inside a hook, such as failures inside $(…)). The recipe is sourced again for every hook, so its top level holds only assignments and function definitions. Lane hooks see the resolved settings, LANE_DIR, LANE_MAIN, LANE_SLUG, LANE_OFFSET, LANE_PROJECT, LANE_MODE, LANE_BASE_BRANCH, and each per-lane port, so a recipe can build values like WEB_URL from WEB_PORT; lane_gc sees only the settings, LANE_MAIN, and LANE_ROOT.
  • The repo's checkout hooks (such as post-checkout) stay off while the engine creates a lane, so they can't run a second setup; lane_setup is the bootstrap, and it runs again on every resume, so it must be idempotent. LANE_CHECKOUT_HOOKS=1 turns them on. On/off settings take 1 or 0.
  • Writing .lanerc changes the repo, so setup is always a user stop, even unattended.
  • Worktrees aren't relocatable — a venv bakes its absolute path into its shebangs — so a lane is rebuilt, never moved.
  • The full contract is references/contract.md; a minimal recipe is references/lanerc.example.

Requirements

Claude Code with plugin support, git, and bash. lane pr also needs the GitHub CLI (gh). Proxy mode needs a reverse proxy the recipe writes routes for, and isolated mode needs a recipe that provisions its own database and stack; host mode needs neither. Dependency installs and dev servers are whatever the stack already uses, called from the recipe.
