create-issue

Turn a validated spec, plan, or conversation into GitHub issues shaped by the repo's own issue templates, with claims executed before creation.

Install

/plugin install create-issue@nautilai

What it does

The skill reads every source artifact in full, then lists the target repo's real labels, issue types, milestones, and .github/ISSUE_TEMPLATE fields so drafting never uses a value the repo lacks. It extracts work-content into a reviewable checklist, asks only the questions the transcript did not settle, shapes each ticket with INVEST and EARS, and drafts work-content only into the template's fields. Before anything is created it greps every cited symbol, runs every verify command and requires it to fail, and dispatches a subagent to audit completeness against the source. Creation waits on explicit approval; epics link sub-issues with native parent and blocked-by edges, and every created issue is diffed back against the source.

Commands / skills

  • /create-issue

    Create issues from the current conversation plus any specs or plans found in the repo.

    explicit slash form only
  • /create-issue path/to/spec.md

    Create issues from a named spec, with the conversation as additional source.

    explicit slash form only
  • /create-issue owner/repo path/to/spec.md

    Target a specific repository instead of the current directory's.

    explicit slash form only
  • /create-issue --dry-run

    Run extraction, shaping, drafting, claim execution, and the audit, then stop: print the drafts, the label, type, and milestone values creation would pass, the blocking graph by title, and the audit findings. Creates nothing.

    explicit slash form only

How it works

Every draft is grounded in what the target repo actually has, then proven before it ships.

1pull ground truthgh label list · issue-types · milestones · ISSUE_TEMPLATE
2extract + question gate~/.claude/plans/ticket-extraction-<slug>.md
3shape with INVEST / EARS
4draft into template fields
5execute every claim
6subagent completeness audit
7approve · create · diff backgh issue create --parent --blocked-by
Under the hood
  • Labels, issue types, milestones, and template fields are read from the target repo at runtime; a value not in that listing is never used. No taxonomy ships with the plugin.
  • Extraction lives in ~/.claude/plans/ticket-extraction-<slug>.md, never in a ticket body. It records the user's answers verbatim so subagents inherit them and cannot regenerate a settled question.
  • Draft budget: target 200 words, hard ceiling 400. Every non-epic ticket carries a Dependencies section; every Find via pattern reappears in Verify Success as a residual check.
  • Claim execution: cited symbols are grepped, verify commands are run and must fail, asserted absences are searched for their negation. Unrunnable claims are marked UNVERIFIABLE.
  • Audit findings are report or ask-user; the audit subagent changes nothing. After creation, removing invented content is auto-fix; adding missed content or cutting length is ask-user.
  • Epics create the parent first, then sub-issues in dependency order with native --parent / --blocked-by edges (needs gh ≥ 2.94.0). Blocking edges live in the relationship graph, never in a comment.
  • A repo with no .github/ISSUE_TEMPLATE/*.yml, or none whose required fields the work can answer, stops the run and asks before a default body outline is used. The chosen template's labels: are passed on --label; gh issue create --body does not apply them.
  • Linear routing runs only when the Linear MCP is reachable and .claude/shoals/create-issue.create-issue.md carries a ## Linear routing mapping; otherwise it is skipped with a reason.
  • Tooling: GitHub MCP preferred, gh CLI as baseline, stop if neither is authenticated.

Requirements

GitHub CLI (gh) authenticated, or the GitHub MCP server configured. Sub-issue and blocking relationships need gh ≥ 2.94.0. Linear routing is optional and needs the Linear MCP plus a project-local shoals mapping.
